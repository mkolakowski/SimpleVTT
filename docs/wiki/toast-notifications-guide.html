Toast notifications v2.43.8

SimpleVTT has two distinct toast surfaces: the dice toast (a transient pop-up that animates the dice for every server roll) and the status toast (a small left-bordered message strip for confirmations, info, and errors). They look different, fire from different code paths, and serve different purposes. This guide documents both — what they show, when they fire, how they're sequenced, and how to use them from new code.

1 · The dice toast — animated roll popup

Fires for every server-side roll the user has visibility to see. Renders a dice-shape SVG, a label, the per-die breakdown, and the total. The dice "wobble" for ~1.4 seconds, then settle on the final values. Click anywhere on the toast to dismiss early; otherwise it auto-dismisses after ~5 seconds.

When the dice toast fires

Broadcast typeWhat the toast shows
rollPlain dice roll from /roll (or any endpoint that broadcasts one). Visibility filter applies.
weapon_attackTwo toasts in sequence: the d20 attack roll first, then 1600 ms later the damage roll (save-DC attacks skip the d20 and fire the damage toast immediately).
spell_cast (with auto_attack_*)Same two-toast sequence as weapon_attack for Fire Bolt / Eldritch Blast / etc.
spell_cast (with auto_save_damage_*)Save-for-half damage toast (Fireball, Sacred Flame, …) — fires after the save-roll toast lands.
feature_used (with dice_* fields)Second Wind / Lay on Hands / Bardic Inspiration / any feature that rolls a die — the heal / bonus die animates as its own toast.
heal_appliedA toast confirming the HP delta when a heal lands on a target via the legacy heal-claim flow.

Sequencing — attack → damage

When a weapon attack or spell attack lands, the server broadcasts a single payload containing both the d20 attack roll AND the damage roll. The client fires the d20 toast immediately, then waits 1600 ms before firing the damage toast. This is enough time for the d20 to land + give a small "breath" between the two animations:

Position + stacking

Tabletop view: bottom-center of the viewport (#roll-toast-container { position: fixed; bottom: 24px; left: 50%; transform: translateX(-50%); }). Multiple toasts stack bottom-up via flex-direction: column-reverse.

Mobile breakpoint: the container moves to center-of-screen + bumps z-index to 500 (so it sits above the touch-friendly UI overlays). Padding grows to 18 px × 28 px so the touch area is comfortable.

Visibility filter

The dice toast respects the same visibility filter as the roll-log card (defense-in-depth):

  • public — toast fires for everyone
  • gm_and_roller — only the GM + the rolling user see the toast
  • gm_only — only the GM sees the toast

Server-side /roll only broadcasts to eligible sockets; the client double-checks before firing. For weapon_attack / spell_cast / feature_used, no visibility field is set — they're always public table actions.

2 · The status toast — confirmations, info, errors

Lightweight bottom-anchored message strips that confirm user actions or surface errors. Distinct from the dice toast: no dice animation, no breakdown — just a colored left border + text.

Lifecycle

  • Fades in from below (~180 ms transform + opacity transition).
  • Holds visible for 4.2 seconds.
  • Fades out (~260 ms) — auto-removed from DOM.
  • Multiple toasts stack vertically in #vtt-toast-stack.

How to fire one from JS

window.showToast is registered globally by app/static/tabletop.js (and fallback-registered by app/static/action_buttons.js for pages that don't load the tabletop bundle): 

// Default kind ('info')
window.showToast('🩹 +6 HP applied to your character!');

// Explicit kind
window.showToast('Encounter saved.', 'success');
window.showToast('Healing failed: ' + error.message, 'error');

When NOT to use a status toast

  • For dice rolls — use the dice toast (it fires automatically off the WS broadcast).
  • For information that needs to persist (HP delta, condition install) — those belong on the roll-log card's pill row, not a transient toast.
  • For modal flows (target picker, confirmation dialogs) — those open their own UI surfaces.

3 · The two surfaces together

Dice toast and status toast can stack. A spell cast that lands a damage roll AND triggers a server error (e.g. expired heal_claim) fires the dice toast and the error status toast in parallel — they live in different containers (#roll-toast-container vs #vtt-toast-stack) and don't collide.

The complementary relationship with the roll log (the persistent card drawer):

  • Dice toast — transient, in-your-face. The "did this just happen?" surface.
  • Roll log card — persistent. The "what happened" audit trail with the ↶ Undo button + the outcome pills.
  • Status toast — transient, peripheral. Confirmations + errors.

A complete weapon-attack flow surfaces all three:

  1. User clicks "Strike" on a weapon — the sheet posts to /attack.
  2. Server broadcasts weapon_attack over WebSocket.
  3. Dice toast #1: d20 to-hit appears at the bottom of the screen.
  4. Roll log card: the attack card lands in the drawer (pill row + dice in ▾ details).
  5. After 1600 ms — dice toast #2: damage dice appear.
  6. If auto-apply was on — the target's HP bar updates in the canvas + initiative tracker.
  7. If the user clicked the ↶ Undo pill on the card — the server reverts, and a status toast confirms ("Reverted 9 damage to Bandit").

4 · Themes — toasts adapt

Both surfaces use the CSS custom properties (--accent, --danger, --c-heal, --bg-2, --border) so all 14 themes (8 core + 6 fantasy) re-tint without per-theme overrides. The bonus chip "+N" on the dice toast borrows --accent for its border + color, so the accent picks up the theme; the status toast's left border switches between var(--accent) / var(--c-heal) / var(--danger) depending on kind.

5 · Where the code lives

  • Dice toast renderer: app/static/roll_toast.js — showRollToast(rollData) entry point; vtt:ws-message CustomEvent listener dispatches off the WebSocket message types.
  • Dice toast CSS: app/static/style.css top section (#roll-toast-container, .roll-toast, .rt-die, .rt-total, .rt-bonus, .rt-out fade-out animation).
  • Status toast renderer: app/static/tabletop.js function showToast(msg, kind), registered as window.showToast. Fallback registration in app/static/action_buttons.js so character-sheet pages also get the helper without loading the tabletop bundle.
  • Status toast CSS: app/static/style.css bottom section (#vtt-toast-stack, .vtt-toast, .vtt-toast-info, .vtt-toast-success, .vtt-toast-error).
  • WS handler that dispatches the toast events: app/static/tabletop.js inside the WebSocket onmessage handler — every incoming message also fires a document.dispatchEvent(new CustomEvent('vtt:ws-message', { detail: msg })) so the decoupled roll_toast.js listener picks it up.
  • Sequencing constant: the 1600 ms attack-to-damage delay is hardcoded in app/static/roll_toast.js in two places (weapon_attack and spell_cast handlers). Both use the same value so behavior stays uniform.
