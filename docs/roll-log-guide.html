The SimpleVTT roll-log v2.42.3

Every action at the virtual table — a die roll, a weapon swing, a spell cast, a class feature use — produces a card in the roll-log drawer on the right side of the tabletop. This page documents the card anatomy, both display modes (verbose default + compact opt-in), and how the log adapts as outcomes land.

The toolbar — switching display modes

At the top of the roll-log drawer is a single button that flips the spell-cast cards between two display modes. The state persists per-user in localStorage (key: simplevtt:rolllog_mode).

The label reads Compact: OFF in verbose mode (default) and Compact: ON in pill-row mode. Click the button to flip; the change applies to all cards rendered after the flip (existing cards in the DOM keep the mode they were rendered with).

Card anatomy — what's always visible vs. tucked away

Every card has the same five-zone structure. The headline is always visible — total, who rolled, target, time. The narrative tail (dice expression, breakdown, flavor text) lives behind a ▾ details toggle that's collapsed by default. This keeps the at-a-glance scan clean while the audit trail is one tap away.

The four card variants

1 · roll — plain dice roll

Emitted by /roll. Headline is the total + a short note ("what was rolled"). The expression and breakdown live in ▾ details. Sample above.

2 · weapon_attack — /attack endpoint result

Carries the attack roll and the damage roll inline (the dice ARE the at-a-glance point of an attack card). Hit / miss / crit verdict is a badge on the attack line. When auto-apply-damage is on, the damage line shows the HP delta and the ↶ Undo button so the GM can revert one click.

3 · spell_cast — the richest variant + the one that has two display modes

Spell-cast cards collect the spell name, target, slot level, and every auto-resolution outcome — heal applied, attack roll vs. AC, save prompt / result, condition install, save-for-half damage. Because there can be a lot to fit, this is the only card type that varies between the verbose ▼ Result block and the compact pill row.

4 · feature_used — class features, racial traits, items

Class features (Second Wind, Rage, Lay on Hands, Cunning Action, Channel Divinity, …) get their own card variant. The header carries a "Class Feature" / "Item" / "Racial Trait" / "Feat" tag — parallel to how spell-cast cards show "Cantrip" or "Lv 1 slot". If the feature has limited uses, a counter chip (0/1 left) appears in the body row. Dice rolls (Second Wind's d10, Lay on Hands' point spend) fire as separate dice toasts; the card stays clean.

Auto-resolution suppresses redundant buttons

When the server-side auto-resolution path (campaign-toggled Auto-apply damage) already rolled the spell's attack / save / damage / heal, the manual "🎲 Roll damage" / "📋 Prompt save" / "🩹 Apply Healing" buttons on the spell-cast card are not rendered. The outcome is already in the ▼ Result block (or the chip row) + the ↶ Undo button is there for one-click revert.

This is gated per-button by the auto-resolution flags carried on the cast payload:

  • auto_heal_applied > 0 → "🩹 Apply Healing" button hidden
  • auto_attack_hit != null → "🎲 Roll {damage}" button hidden (the auto-attack ran, regardless of hit / miss outcome)
  • auto_save_target_kind != null → "📋 Prompt save" + "🎲 Roll damage" buttons hidden (PC was prompted or NPC was auto-rolled)

Spells with no auto-resolution path (Magic Missile auto-hits, Misty Step utility) keep their manual buttons because the auto-flags stay null on those payloads.

The "Roll damage" button — fallback behavior

For spells that still surface a manual damage button (Magic Missile, Scorching Ray with no auto-attack, homebrew utility cantrips):

  • Clicking the button rolls the damage as the caster — not as some other token the GM happens to own. The new roll-log entry's note reads {Spell} damage (as {Caster}).
  • The button hides itself on a successful roll so the card visually commits to its result state.
  • On HTTP failure the button re-enables so the user can retry.

Themes — the log adapts

The roll-log layout uses CSS custom properties so all eight built-in themes re-tint the ▼ Result block + chip pills without per-theme overrides. Outcome colors (heal=green, damage=orange, crit=amber, buff=cyan, miss=danger) carry semantic meaning and stay consistent; the block accent and chip surface follow the theme.

Persistence + visibility

Roll-log cards survive page refreshes via localStorage (key simplevtt:rolllog:${CAMPAIGN_ID}, last 100 WS-only entries, FIFO trim). Server-rendered Jinja roll history at page load still comes down fresh and re-renders through the same append functions — so the new layout applies to historic rolls too.

Each roll event carries a visibility field:

  • public (default) — broadcast to everyone in the campaign.
  • gm_and_roller — GM + the rolling user only. Card has an amber "GM + you" badge + border.
  • gm_only — GM only. Card has a danger-colored "GM only" badge + border.

weapon_attack / spell_cast / feature_used are always public — they reflect public table actions.

Where the code lives

  • Card rendering: app/static/tabletop.js — appendRoll, appendSpellCast, _appendFeatureUsed, appendWeaponAttack, appendRollRequest.
  • Result-block / chip toggle: same file — _rollLogMode, _setRollLogMode, _spellResultSummary, _spellResultChipsHtml, _spellResultBlockHtml.
  • Persistence: same file — _persistRollEntry + _hydrateRollLog.
  • Card CSS + toggle CSS: app/templates/tabletop.html — inline <style> block.
  • Theme tokens (incl. --c-heal / --c-crit / --c-damage / --c-buff): app/static/style.css.
  • Dice toast (separate transient surface): app/static/roll_toast.js.
